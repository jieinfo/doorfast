# 初始来电请求的抓包缺口

## 摘机应答复核

新增库内 `df_gvs_session_observe_pick`：已有振铃或预览会话时，
先记录本机六字节源地址发往当前对端的 0x03 请求，再接受反向 0x83 应答。
两帧均要求七字节载荷；匹配期间绑定本机会话 generation 和初次请求时间。
重传不延长窗口，错误目的分机、孤立应答、超时或跨 generation 均不推进通话。
超时时间由调用方指定；测试使用 3000 毫秒，这不是已证明的厂商常量。
这一接口已接入 PCAP 时间戳处理；常驻服务另外使用共享单调截止时间，在无新包时也会检查超时。
离线回放暂采用显式的 3000 毫秒分析窗口；它是项目分析策略，不是厂商常量。
合成 PCAP 测试覆盖请求后一秒的正确应答、三秒边界应答、错误对端。
CLI 新增 talking（进入通话状态次数）和 pick_rejected（关联失败摘机帧数）。
实际 incoming-three 回放得到 talking=0、pick_rejected=8；由于缺少初始
来电帧，没有现存会话可关联，程序不会补造一个已建立的通话。
报文没有经过可用会话标识验证，因此相同地址窗口内的旧报文仍无法可靠区分。
本轮验证为本机 macOS ARM64 编译与单元测试，不是 ImmortalWrt x86_64 APK 验证。

c.smali 的 i([B,String,int) 明确记录 sendPickReply，并写入
family 0x03、opcode 0x83、七字节载荷。
TalkBackBusiness 的 e(Message) 分支先比较来源地址与当前会话对端的全部
六字节，再调用后续处理；这不是无条件建立新会话的入口。
对应抓包在 pick 日志后出现反向 0x83，随后日志倒计时从振铃阶段切换到通话阶段。

Doorfast 现将长度一致且载荷七字节的 0x03/0x83 标为
PickReplyObserved。该事件只说明观察到应答形状；会话模块不会单凭它
进入 TALKING。后续必须关联先前的摘机请求、报文方向、当前对端及超时。
测试覆盖七字节识别、零载荷不识别、孤立应答不推进会话。

本次独立读取四份原始 Ethernet/IPv4 PCAP，按 UDP/8300 的 GVS
公共头统计操作码：四份文件均未发现 family=0x03、opcode=0x01。
因此当前只接受 0x01 来电候选的观察器返回零，不能解释成设备没有接到来电。

## 交叉证据

`gvs-incoming-three-20260907-logcat.txt` 第 221 行起记录：

- 20:37:21.502：`NormalStandByDeal-->1`，随后 `sendCallReply`。
- 20:37:21.503：`sendVedioAsk`、`startHand`。
- 20:37:21.512：`startCountDown`。
- 20:37:25.372：`pick`；20:37:25.379：`sendPickAsk`。
- 20:37:26.606：倒计时 119（此前振铃倒计时为 29、28 等）。

对应 PCAP 最先可见的控制帧在 20:37:21.529821，操作码 0x81，
由室内机类型 0x61 发往门口机类型 0x32；随后是 0x55。
全文件有 18 个 0x81、6 个 0x55，未记录任何 0x01。
日志与抓包时间可能存在偏差，但操作码及方向同样支持此结论。

这是“应用处理了请求，但该请求未见于本批抓包”的证据。
尚不能确定是采集过滤、采集位置、多播路径还是丢包；不能任选一个解释当事实。

## 长度校验的九次拒绝

该 PCAP 有八个 0x03/0x56：声明载荷长度为 1，实际载荷为 0；
另有一个 0x04/0x09：声明载荷长度为 12，实际载荷为 8。
它们对应现有回放输出的九次 invalid。此次未放宽严格长度校验。
后续需要对照各操作码的原始构造逻辑，区分实现瑕疵、特殊约定和抓包截断。

## 状态语义更正

0x51/0x52 的静态日志名 sendHandAsk/sendHandReply，以及通话中的
周期性出现，支持握手维护解释；此前文档称其为挂断的表述撤回。
不能因这两个操作码结束会话。摘机相关的 0x03/0x83 在抓包中也存在，
下一步应结合 pick 日志建立状态转换夹具。

## 实现依据与限制

不以 0x81 伪装成收到初始来电请求。完整 PCAP 回放会话测试仍缺少 0x01
的原始帧，可先用静态构造规则产生明确标注的合成夹具，验证解析和状态逻辑。
主机模式仍需在线维护、双向应答、媒体协商及摘除室内机后的现场互操作验证。
