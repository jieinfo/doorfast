# Doorfast 串联观察现场步骤

当前状态：开发验收中，尚未放行现场插线。本文件描述放行后的操作流程。

## 插线前的软件门槛

- 目标 APK 构建成功，记录下载来源、提交号和 SHA-256。
- 虚拟机通过记录器自测、真实 ubus 状态、LuCI 刷新及桥接演练。
- 桥接演练验证双向转发，以及单独停止 Doorfast 和记录器后继续转发。
- 实机预检通过，核实独立磁盘、接口角色和回退线。

任一项尚未完成，都不能把构建成功当作现场放行。

## 1. 保留现有接线，核对设备

记录 ImmortalWrt 的三个接口角色：VLAN 10 管理、门禁上联、MT8157 下联。
逐一核对系统接口名、MAC 地址与机箱面板位置；不要按接口编号推测。
管理口保留现有连接。确认 MT8157 独立供电，并停用其备用网络连接。

备份 ImmortalWrt、交换机和 iKuai 配置，备份另存到管理电脑。
核实 `/mnt/doorfast` 是独立持久磁盘挂载，容量足够且至少保留 6 GiB 可用空间。
准备并标记交换机直连 MT8157 的回退网线。

APK 安装前核对 `apk --print-arch`、固件版本以及 APK 校验和。
仅安装经过本项目目标构建和虚拟机验收的文件。开发包若未签名，应逐个确认来源，
不修改系统全局签名验证设置。安装后保持两个服务关闭。

## 2. 在维护窗口准备透明桥

使用已核对的两个空闲物理接口，由管理员创建 `br-door`。
该桥仅含门禁上联和 MT8157 下联，不含管理口。
桥和两个成员端口不得有 IPv4/IPv6 地址或 DHCP 客户端；关闭桥上的 STP、
组播侦听及主动发现服务，保持与其他 VLAN 隔离。
交换机连接门禁上联的端口使用 VLAN 40 无标签 Access 配置。

Doorfast APK 不创建网桥。现场接口名称未确认前，不提供可直接粘贴的网络修改命令。
在 `/etc/config/doorfast-deployment` 填写核实过的接口角色。
观察配置保持 `passive_only=1`，记录器保持 `recording_enabled=0`。部署配置中的
`observation` 必须显式选择 `br-door`、门禁上联或 MT8157 下联之一；先在隔离环境
验证该接口确实能看到双向转发报文。虚拟机验证表明桥接口是否可见取决于系统抓包
实现，因此不能未经验证固定为 `br-door`。

执行 `doorfast --preflight /etc/config/doorfast-deployment`，必须退出 0 且返回
`safe: true`。未通过时按具体失败项处理后重新检查。

## 3. 首次插线，仅验证 MT8157

在约定维护窗口，将原交换机至 MT8157 连接改为：

交换机 VLAN 40 Access 口 → Doorfast 门禁上联 → br-door → 门禁下联 → MT8157。

Doorfast 与记录器此时保持关闭。验证原有来电、接听、开门、电梯以及上线状态。
只测试本户已有且获授权使用的功能。任一功能异常立即恢复原直连，保存异常时间。

确认系统桥接转发正常后，分别比较桥及成员端口的短时观察结果，选定唯一观察口，
避免重复计数。当前记录器使用部署配置中的桥接口；若实际证据要求成员口捕获，
必须先完成该配置能力及测试，再开启长期记录。

## 4. 启用观察

先在虚拟机执行固定路径记录器自测，不在现场盘上制造低空间。
现场启用记录器前确认状态展示、预算和空间保护已通过验收。
将 `recording_enabled` 设置为 `1`，启动独立 `doorfast-recorder` 服务；
将 Doorfast 的观察接口设为已验证接口，保持被动模式，再启动 Doorfast。

检查 LuCI 中上联、下联、管理链路和记录器状态。`陈旧`、`读写错误`、
`磁盘余量保护`或任何未知链路信息都需要调查，不能视为正常记录。
记录器不自动重启，避免空间不足时不断重复启动。

记录插线前后时间，保存本地快照与人工功能验证结果。
原始 PCAP 和完整地址仅保留本地管理员访问，不提交到 GitHub。

## 5. 观察与回退

至少连续观察七天，覆盖日常来电、开门和已存在的电梯使用。
每天检查链路错误、丢包、磁盘余量、记录器状态和 MT8157 业务表现。
长期观察通过只证明串联学习部署稳定，不证明 Doorfast 已能替代 MT8157。

出现异常先停止两个观察服务。如异常仍存在，将交换机直接接回 MT8157。
Doorfast 整机断电、系统崩溃、网卡故障或桥配置错误都可能中断 MT8157 网络；
软件桥没有断电自动旁路能力，恢复依赖人工回退接线。
