# GVS 公共头提供器契约

Doorfast `r9` 将公共头的两个 8 字节不透明字段改为由带完整帧上下文的可替换提供器生成。该接口只建立离线实现边界，不包含旧库、密钥、认证算法或网络发送能力，也不代表现有占位实现可被真实设备接受。

## 输入与输出

提供器收到只读 `df_gvs_header_request`：

| 字段 | 含义 |
|---|---|
| `destination` | 6 字节目标逻辑地址 |
| `source` | 6 字节本机逻辑地址 |
| `family` | 功能码，例如候选在线族 `07` |
| `opcode` | 操作码，例如探测应答 `81` |
| `payload` | 载荷只读视图；零长度时允许为空 |
| `payload_length` | 两字节小端长度字段所表达的载荷长度 |

提供器只能填写 `random_code[8]` 与 `encryption_code[8]`。序列化器先在栈上生成这 16 字节，只有提供器返回 `DF_OK` 后才写入输出帧。提供器失败时输出长度归零，调用者原有缓冲区保持不变。

## 当前占位实现

生产守护进程仍显式选择 `df_gvs_placeholder_header_fields`：它对两个字段填零，并在日志中标记 `header=placeholder mode=memory`。它只服务于完整 42 字节公共头、长度、地址和事务状态机的离线验证。项目没有把“回读成功”解释为认证成功，也没有为该实现开放真实传输入口。

## 替换边界

未来由 Doorfast 项目自身维护的兼容实现必须满足同一契约：

1. 只依赖请求结构和提供器私有上下文，不修改请求指向的数据；
2. 对不支持的功能码、操作码或载荷明确失败；
3. 每次调用完整写入两个 8 字节字段，不向日志暴露字段、密钥或原始载荷；
4. 先通过固定向量、失败原子性、常规构建及 Sanitizer 测试；
5. 在另一个明确评审的里程碑中验证字段来源和设备兼容性，之后才能讨论独立的受控发送适配器。

`tests/test_gvs_serialize.c` 已覆盖 `07/81` 完整上下文、`91/02` 零载荷上下文，以及提供器写入临时字段后返回失败时的输出原子性。原有同步帧、对端模拟器和内存事务继续通过同一生产序列化入口。

GitHub Actions `34321275520` 构建的 `doorfast-0.1.0-r9.apk` 已从 r8 升级安装到 ImmortalWrt 25.12.1 x86/64 隔离虚拟机。服务、ubus 和 LuCI 冒烟通过；两个固定 `07/01` 均经过实际抓包入口生成新的 48 字节占位公共头内存帧并到达模拟成功终态，同步版本 8、在线候选和本户来电回归均通过。这验证了目标工具链中的接口兼容性，不改变占位实现不可用于真实互操作的结论。
