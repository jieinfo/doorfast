# Doorfast 完整主机模式与 ImmortalWrt APK 项目规划

更新：2026-09-08。这是后续开发与验收的主路线；历史被动阶段设计保留为阶段记录。

## 1. 最终交付目标

在 ImmortalWrt **25.12.1、x86/64、x86_64** 上安装 Doorfast 原生 APK 软件包，由 Doorfast 独立承担已验证 GVS 室内机的网络角色。MT8157 断电、断网后，仍能上线、被呼叫、通知用户、应答、双向通话、按配置控制门禁并正常结束和恢复。

这里的 APK 是 ImmortalWrt 软件包，不是 Android APK；目标为 64 位 x86，不包含 32 位 i386。最终程序不需要 Android、ARM 模拟器、旧 Doorlink 进程或旧版激活服务。Doorfast 自身不设置闭源激活门槛；对端设备的协议认证和配置凭据属于互操作要求，不能由取消 Doorfast 激活自动替代。

“完整”以项目维护的 **GVS 功能范围** 定义，不承诺旧 Doorlink 所有品牌，也不恢复贡献者提交协议证据或第三方适配入口。项目自身维护协议、测试和设备配置档案。

| 最终能力 | 验收结果 |
|---|---|
| 独立身份与在线维护 | 屏幕离线后，Doorfast 冷启动完成必要上线，门口机可定位本户；重启和网络恢复后可重新上线 |
| 来电与会话 | 目标房间过滤、来电通知、重传、忙线、优先级抢占、应答、拒接、挂断、超时均有明确行为 |
| 音视频 | 用户端能看到门口机画面，双向音频可用，音视频随会话建立和释放；协议中不支持的方向不虚构 |
| 门禁控制 | 本户已纳入支持范围的开门等动作得到对端确认，成功、拒绝和超时可区分 |
| 电梯和扩展业务 | 已确认存在的召梯、楼层选择、监看、室内机同步、转接等逐项列入验收；无设备或无证据项目不得标记完成 |
| 产品使用 | 可通过管理界面选择本机接口、配置身份、查看状态、诊断与升级；用户操作有明确反馈 |
| 交付 | 源码、可复现构建说明、x86_64 APK、依赖及版本信息、校验和、发布说明、安装/升级/卸载文档齐全 |

电梯及扩展能力若是声明支持的安装环境所必需，就属于该环境的完整验收项；不能用“可选”掩盖功能缺失。尚不清楚的业务先列为研究缺口，未验收时只能发布标明范围的预览版。

## 3. 架构与实现原则

继续使用原生 C 服务作为协议和会话核心，通过 procd 管理生命周期、UCI 管理配置。协议业务、传输、计时、媒体和用户接口分开，离线回放与实际服务共用协议/会话逻辑，分别提供捕获时间和单调运行时间。

服务运行在 ImmortalWrt；LuCI 提供配置、状态和操作入口。MT8157 拆除后，通话的扬声器、麦克风和显示由用户的浏览器或移动终端承担。浏览器媒体接口是否需要 WebRTC 网关，须在媒体阶段根据已确认编解码和资源测试选型；不能默认把原始 GVS UDP 直接交给浏览器。Home Assistant/MQTT/Webhook 为集成能力，不成为门禁服务运行的必需依赖。

接口由用户从本机现有物理口、VLAN、bridge 或 bond 中选择，不限定 eth0/wlan0。门禁接口、可选上行接口和逻辑身份分别配置。网络路由、VLAN 及防火墙的必要前提在安装向导中展示；默认不自动改写整机网络。

后续拟新增模块按职责划分：运行入口、UCI 加载、GVS 传输、身份在线维护、请求事务、媒体、本地 API 和升级。具体 C 接口在各阶段开始时依据真实调用方确定，不在总规划中虚构尚无证据的协议字段。

### M2：优先验证独立身份、上线和来电定位

输入：IndoorSyncBusiness、SDK 初始化、地址表及现有私有抓包分析。拟新增身份在线状态与发送事务模块。

- [ ] 逐项确定身份由配置还是网络分配，本户、分机、主从角色、IP/端口如何进入地址表。

- [ ] 明确网络认证依赖、合法配置/凭据来源及独立实现接口；不能用“接收链未见校验”推断发送端可省略认证。
- [x] 建立本地纯内存协议对端测试环境，验证选举生命周期、固定轮次、维护者失联接管和来电目标路由；该结果不代表真实网络上线或设备认可。
- [ ] 在用户自有环境以可恢复方式让 MT8157 离线，验证 Doorfast 冷启动后仍能收到门口机的实际来电。

交付：独立在线维护实现、测试记录及实机结论。关键验收：没有 MT8157 在线时，门口机主动把本户呼叫交给 Doorfast；至少覆盖门口机重启、Doorfast 重启和网络短时断开。

这是最高优先级的不确定性关口。静态研究与本地模拟可以先完成；若没有可用设备，记录“等待实机验收”，继续推进 M1、包测试和有证据的模块，但不得把 M2 标成实机通过。

进展记录：逻辑身份由配置注入、六字节 BCD 布局、确定性业务 IP、住宅组播 IP 和同户五个候选终端的生成规则已经实现并完成离线测试，见 `gvs-identity-addressing.md`。`07/01` 请求接收和 `07/81` 回复构造也已按旧 APK 调用顺序离线实现：已知候选会刷新在线状态，未知来源仅形成待回复对象。`r6` 增加 16 项固定容量、1 秒失效、精确重复合并和失败原子性的离线回复队列；`r7` 将队列接入单事务状态机，覆盖发送中、成功、失败、三次重试上限、单次超时和迟到结果隔离；`r8` 将事务接入完整 48 字节 `07/81` 内存构帧与生产解析器回读校验。生产运行时仍没有 UDP 发送，公共头的两个 8 字节字段明确使用全零占位值。该项保持未完成，因为主从角色的全部业务含义、合法公共头提供器以及门口机侧接受行为尚未形成发送闭环和实机证据。

在线维护调度已形成无网络发送副作用的 C 状态机，覆盖 3 秒启动等待、三轮同步询问、三轮版本询问、30 秒候选探测、60 秒离线判定、维护者周期同步和断网重启，见 `gvs-presence-lifecycle.md`。选举回复、周期数据及被动运行时接收均已接入；动作在当前运行模式只形成诊断日志。

发送端已增加通用 42 字节控制帧序列化器，并覆盖候选探测、同步询问和同步版本询问。两个 8 字节公共头字段必须由外部提供器成功生成，未配置时构帧失败。`91/81`、`91/82` 已接入离线在线维护状态机，包含阶段门控、版本与分机号条件、长度和地址校验。

周期数据层也已完成离线闭环：支持 `91/03` 的 `Normal`/`Period` JSON、20 项分片、JSON 转义、本地版本递增与 60000 回绕、入站事务应用、版本/分机号冲突决策，以及非维护者连续缺失两轮后的接管。被动运行服务现已分流同步帧，记录角色决策，并把变化后的版本原子保存到独立 UCI 文件；抓包掉线恢复会保留版本和同步表并重新开始上线阶段。首批两个静态确认的 MiniOS 同步字段已登记为 Doorfast 自维护适配器，但因其敏感属性默认禁用，只有显式提供非空值后才进入同步存储。运行时提供脱敏状态快照和 JSON 查询，可输出阶段、维护角色、版本、在线候选数量、适配器计数与最近接收结果，作为后续 ubus/LuCI 状态页的数据边界。证据见 `2026-09-08_reverse-gvs-sync-report.md`。仍缺适配器合法值来源、公共头字段的设备兼容性验证和实机联调；当前无 UDP 发送。

本地 GVS 对端模拟器现已通过生产序列化与接收入口验证三轮选举、低分机号让位、一个有效周期后的两轮失联接管，以及本机/同户/其他住户的来电目标选择。`07/01` 请求与 `07/81` 候选在线应答的静态语义均已确认并离线接入：请求可生成“请求前两字节加四个零”的待回复帧，已知候选会重复刷新 60 秒在线期限，状态通过 `online_peers` 展示；运行时不发送该回复。隔离 ImmortalWrt 25.12.1 x86_64 虚拟机已验证固定 UDP 帧可经过目标网卡进入 `r5` APK：`07/01` 产生被动待回复记录并刷新已知候选，`07/81` 被独立接收，`Period` 刷新维护期限，`Normal` 把版本 8 持久化到 UCI，本户来电产生 `IncomingCall`；此前 `r4` 已验证候选 60 秒离线和两个缺失周期接管。真实门口机接受性仍是 M2 的实机缺口。

## 5. 依赖、优先级与推进方式

依赖关系：M0 → M1；M2 的证据工作可与 M1 并行，实际在线验收依赖 M1；M2 → M3 → M4；M5 的配置/管理可与 M3/M4 并行；P 贯穿各阶段；M1–M5 和 P 完成后进入 M6。

近期按这个顺序执行：

1. 修正 `--config` 与 procd 的运行契约，提供能运行的被动服务和目标 APK。
2. 集中核实独立上线/来电定位的最小闭环，把认证与身份依赖列成可验证问题。
3. 尽早做一次 MT8157 离线的来电验证，或记录阻碍该验证的具体条件。
4. 以实际闭环为依据补信令发送、媒体和用户端，持续验证目标 APK。

不继续无限扩充离线统计来推迟上线验证。离线解析仍需维护，但它是主机实现的测试基础，不是最终验收替代品。

总工期暂不作日历承诺：M2 的协议与实机结果决定后续实现难度。每个里程碑结束时报告交付物、通过的证据层次、遗留缺口和下一阶段工作量；现场验证不可用时明确区分“开发完成”和“验收完成”。
