# Doorfast 完整主机模式与 ImmortalWrt APK 项目规划

更新：2026-09-08。这是后续开发与验收的主路线；历史被动阶段设计保留为阶段记录。

## 1. 最终交付目标

在 ImmortalWrt **25.12.1、x86/64、x86_64** 上安装 Doorfast 原生 APK 软件包，由 Doorfast 独立承担已验证 GVS 室内机的网络角色。MT8157 断电、断网后，仍能上线、被呼叫、通知用户、应答、双向通话、按配置控制门禁并正常结束和恢复。

这里的 APK 是 ImmortalWrt 软件包，不是 Android APK；目标为 64 位 x86，不包含 32 位 i386。最终程序不需要 Android、ARM 模拟器、旧 Doorlink 进程或旧版激活服务。Doorfast 自身不设置闭源激活门槛；对端设备的协议认证和配置凭据属于互操作要求，不能由取消 Doorfast 激活自动替代。

“完整”以项目维护的 **GVS 功能范围** 定义，不承诺旧 Doorlink 所有品牌，也不恢复贡献者提交协议证据或第三方适配入口。项目自身维护协议、测试和设备配置档案。

| 最终能力 | 验收结果 |
|---|---|
| 独立身份与在线维护 | 屏幕离线后，Doorfast 冷启动完成必要上线，门口机可定位本户；重启和网络恢复后可重新上线 |
| 来电与会话 | 目标房间过滤、来电通知、重传、忙线、优先级抢占、应答、拒接、挂断、超时均有明确行为 |
| 音视频 | 用户端能看到门口机画面，双向音频可用，音视频随会话建立和释放；协议中不支持的方向不虚构 |
| 门禁控制 | 本户已纳入支持范围的开门等动作得到对端确认，成功、拒绝和超时可区分 |
| 电梯和扩展业务 | 已确认存在的召梯、楼层选择、监看、室内机同步、转接等逐项列入验收；无设备或无证据项目不得标记完成 |
| 产品使用 | 可通过管理界面选择本机接口、配置身份、查看状态、诊断与升级；用户操作有明确反馈 |
| 交付 | 源码、可复现构建说明、x86_64 APK、依赖及版本信息、校验和、发布说明、安装/升级/卸载文档齐全 |

电梯及扩展能力若是声明支持的安装环境所必需，就属于该环境的完整验收项；不能用“可选”掩盖功能缺失。尚不清楚的业务先列为研究缺口，未验收时只能发布标明范围的预览版。

## 2. 当前基线：已经有什么、尚缺什么

本节依据当前工作树文件，不把历史构建成功或测试模型等同于完整服务。

| 组件 | 已有成果 | 下一缺口 |
|---|---|---|
| GVS 解码 | 42 字节公共头、声明长度检查、身份前五字节过滤、部分事件识别 | 操作码载荷语义、错误事件映射、网络分片及异常边界仍需补齐 |
| 会话核心 | 来电/通话/结束、摘机关联、代次隔离、振铃抢占、共享单调计时及网络中断清理 | 媒体与控制事务联动 |
| 离线回放 | 双事件抢占、计时同步、挂断/抢占/超时分类、合成与混合回归 | 持续运行服务不能依赖 PCAP 后续记录推进时间 |
| 网络服务 | `--config` 配置加载、只读抓包循环、信号停止、完整已知接收事务及有限接口重开 | 目标系统长期运行仍需验证 |
| 安装脚本 | procd 启动脚本、UCI 配置样例及匹配的运行入口 | 仍需在目标系统验收启停、重启和配置保留 |
| 协议发送 | 静态调用链及公共头字段角色的分析 | 独立上线、发送端封装、请求/应答和设备接受均未形成完整验证 |
| 媒体 | 既有分析材料 | x86 接收/发送、用户播放/采集端与媒体释放链尚未交付 |
| APK | SDK 构建配方及 GitHub Actions，历史有构建成果 | 本轮代码还没有新的目标 APK 验证；可安装、可运行、可交互需分别验收 |
| 管理与升级 | 既有 GitHub 升级方向 | LuCI、可使用的本地管理 API、升级验证与恢复尚需开发 |

主要证据：[静态分析](libencrypt-arm64-analysis.md)、[抢占实现与测试](gvs-preemption-model.md)、[混合回放](gvs-hybrid-regression.md)。原始抓包缺少部分初始来电请求；补入合成请求后的回归只能证明观察逻辑，不能证明真实上线或发送互操作。

## 3. 架构与实现原则

继续使用原生 C 服务作为协议和会话核心，通过 procd 管理生命周期、UCI 管理配置。协议业务、传输、计时、媒体和用户接口分开，离线回放与实际服务共用协议/会话逻辑，分别提供捕获时间和单调运行时间。

服务运行在 ImmortalWrt；LuCI 提供配置、状态和操作入口。MT8157 拆除后，通话的扬声器、麦克风和显示由用户的浏览器或移动终端承担。浏览器媒体接口是否需要 WebRTC 网关，须在媒体阶段根据已确认编解码和资源测试选型；不能默认把原始 GVS UDP 直接交给浏览器。Home Assistant/MQTT/Webhook 为集成能力，不成为门禁服务运行的必需依赖。

接口由用户从本机现有物理口、VLAN、bridge 或 bond 中选择，不限定 eth0/wlan0。门禁接口、可选上行接口和逻辑身份分别配置。网络路由、VLAN 及防火墙的必要前提在安装向导中展示；默认不自动改写整机网络。

后续拟新增模块按职责划分：运行入口、UCI 加载、GVS 传输、身份在线维护、请求事务、媒体、本地 API 和升级。具体 C 接口在各阶段开始时依据真实调用方确定，不在总规划中虚构尚无证据的协议字段。

## 4. 阶段路线与验收关口

### M0：整理可追溯基线

目标：每项功能都能回答“证据在哪里、代码在哪里、如何验证”。

- [x] 汇总当前未提交工作，审阅后按协议、会话、部署形成可追溯版本记录；保留用户已有改动。
- [ ] 建立项目内部功能清单，给每项标注：静态确认、抓包观察、离线通过、目标系统通过、实机通过。
- [x] 校正 README 的早期描述、安装包 Dnake 标题及 GVS 主线命名。
- [x] 排定已知正确性问题：操作码映射、最小载荷长度、分片处理、配置数字边界、未知类型与拒绝原因。

交付：准确的开发基线和发布缺口清单。验收：任何“已完成”的条目都有可定位代码或验证记录，不再用重复小步统计修改代替主机模式核心进展。

### M1：可安装、可持续运行的原生服务

主要文件：`src/main.c`、`src/config.c/.h`、`src/capture.c`、`src/gvs_observer.c`、`src/gvs_session.c`、`package/doorfast/files/*`，新增运行与 UCI 加载模块及对应测试。

- [x] 实现 `--config`、配置加载、初始化失败退出码、正常停止和信号处理。
- [x] 以实际选定接口接入 GVS 接收，配置缺失或接口失效给出可操作诊断。
- [x] 将会话计时从回放局部变量抽成可共享的计时状态；空闲无包时也能超时。
- [x] 明确服务重启、接口掉线、配置变化时的会话清理和恢复；限制队列及重试次数。
- [ ] 验证 procd 启停、开机行为、配置保留和不重复创建实例。

交付：目标系统上能长期运行的被动服务 APK。验收：在 x86_64 虚拟机完成安装、启用、接收、空闲超时、停止、重启；不会因为入口不匹配而反复退出。这只是运行平台验收。

### M2：优先验证独立身份、上线和来电定位

输入：IndoorSyncBusiness、SDK 初始化、地址表及现有私有抓包分析。拟新增身份在线状态与发送事务模块。

- [ ] 逐项确定身份由配置还是网络分配，本户、分机、主从角色、IP/端口如何进入地址表。
- [ ] 列出上线、刷新、退出、重试和重复身份处理所需消息；区分已知与待证实字段。
- [ ] 明确网络认证依赖、合法配置/凭据来源及独立实现接口；不能用“接收链未见校验”推断发送端可省略认证。
- [ ] 建立本地协议对端测试环境，验证上线生命周期、有限重试和故障恢复。
- [ ] 在用户自有环境以可恢复方式让 MT8157 离线，验证 Doorfast 冷启动后仍能收到门口机的实际来电。

交付：独立在线维护实现、测试记录及实机结论。关键验收：没有 MT8157 在线时，门口机主动把本户呼叫交给 Doorfast；至少覆盖门口机重启、Doorfast 重启和网络短时断开。

这是最高优先级的不确定性关口。静态研究与本地模拟可以先完成；若没有可用设备，记录“等待实机验收”，继续推进 M1、包测试和有证据的模块，但不得把 M2 标成实机通过。

### M3：完整呼叫信令和控制事务

主要文件：现有 `gvs_session`、`gvs_priority`、`gvs_observer`，新增请求事务和发送传输模块。

- [ ] 把已验证的接收状态机扩展为主动应答、拒接、挂断、忙线及有限重试。
- [ ] 保证抢占时旧结束事件、旧计时与媒体清理先于新来电；新会话不继承旧摘机等待。
- [ ] 逐条核实同步、握手、转接等操作的作用范围；同来源迟到报文仍不确定时显式限制相关行为。
- [ ] 为每个控制动作建立目标、当前状态、请求关联、确认/拒绝/超时和重复请求处理。
- [ ] 实现本户门禁所需开门；将召梯、楼层和其他已确认 GVS 功能逐项实施并验收。

交付：有请求/应答闭环的信令与控制实现。验收：业务逻辑测试、异常报文测试和实际设备流程分别通过；不能把“已经发送”反馈为“已经开门”，不能因用户重复点击产生无界重复动作。

### M4：用户可用的音视频通话

- [ ] 核实音视频消息布局、协商字段、编解码、分片重组、时间/序列语义及端口生命周期。
- [ ] 实现接收画面、双向音频、抖动/丢包处理、静音和会话结束后的资源释放。
- [ ] 完成浏览器或移动端的播放与麦克风接入路径；对其传输网关、依赖、CPU/内存开销做目标系统测试。
- [ ] 验证来电、接听、挂断、抢占、超时和掉线时的媒体切换，不串入上一通会话。

交付：屏幕离线后的真实端到端通话。验收：用户能收到通知、查看画面、听说通话并结束；编解码支持与延迟实测写入发布说明。只有抓包元数据解析不算此阶段完成。

### M5：管理、集成及 GitHub 升级

- [ ] 提供 LuCI 页面：接口选择、逻辑身份、在线角色、当前会话、功能开关及诊断。

主要文件：`.github/workflows/build-apk.yml`、`package/doorfast/Makefile`、`scripts/prepare-sdk-package.sh`、包清单和 CLI 测试；管理界面新增 `luci-app-doorfast` 包目录。

- [ ] 虚拟机使用 ImmortalWrt 25.12.1 x86_64 验证首次安装、启停、配置迁移、升级、降级恢复和卸载。
- [ ] 每阶段产出开发 APK；只有通过最终功能验收的版本标注完整主机模式。

APK 构建从 M1 开始持续验证，不等待 M4/M5 完成。当前 CI 已有 SDK 下载与编译路径，仍需补目标系统运行和发布验证。

### M6：替代验收与稳定发布

以下为项目建议的验收标准，不是厂商性能承诺：

- [ ] MT8157 全程离线，完成至少 100 次来电/应答/挂断循环；覆盖重传、忙线、抢占、超时和连续来电。
- [ ] 连续运行至少 72 小时，统计异常退出、内存增长、队列增长、音视频资源释放及在线刷新情况。
- [ ] 验证服务、系统及门口机重启，网络断开恢复，配置错误与重复身份的可诊断行为。
- [ ] 对声明支持的开门、电梯及扩展功能分别完成实际验收；动作与反馈一致，无错误目标或非预期重复动作。
- [ ] 完成从干净系统安装到配置、使用、升级和恢复的整套操作记录。
- [ ] 发布明确版本和范围的 APK、源码版本、依赖信息与使用文档；保留现场恢复方案。

## 5. 依赖、优先级与推进方式

依赖关系：M0 → M1；M2 的证据工作可与 M1 并行，实际在线验收依赖 M1；M2 → M3 → M4；M5 的配置/管理可与 M3/M4 并行；P 贯穿各阶段；M1–M5 和 P 完成后进入 M6。

近期按这个顺序执行：

1. 修正 `--config` 与 procd 的运行契约，提供能运行的被动服务和目标 APK。
2. 集中核实独立上线/来电定位的最小闭环，把认证与身份依赖列成可验证问题。
3. 尽早做一次 MT8157 离线的来电验证，或记录阻碍该验证的具体条件。
4. 以实际闭环为依据补信令发送、媒体和用户端，持续验证目标 APK。

不继续无限扩充离线统计来推迟上线验证。离线解析仍需维护，但它是主机实现的测试基础，不是最终验收替代品。

总工期暂不作日历承诺：M2 的协议与实机结果决定后续实现难度。每个里程碑结束时报告交付物、通过的证据层次、遗留缺口和下一阶段工作量；现场验证不可用时明确区分“开发完成”和“验收完成”。

本规划编制时，仅核对本地代码、现有 SDK 配方和证据记录；没有启动新的远程构建、部署或实机动作。最终发布必须记录 APK 实际安装运行与独立设备互操作结果。
