# GVS 离线回复队列

Doorfast `r6` 为已解析的 `07/01` 请求增加固定容量的内存回复队列。`r7` 已将 FIFO 取出接入[离线发送事务](gvs-offline-send-transaction.md)，运行时仍只调用模拟发送器，不创建真实网络发送路径。

## 消息与队列映射

| 输入/动作 | 功能码/操作码 | 载荷 | 当前处理 |
|---|---|---|---|
| 候选探测请求 | `07/01` | 恰好 2 字节 | 严格解析并生成待回复对象 |
| 待回复对象 | 内存结构 | 目标地址、请求 2 字节、候选观察标记 | 进入固定容量队列 |
| 候选探测应答 | `07/81` | 请求 2 字节加 4 个零 | 已有序列化器可构造，运行时只完成模拟事务 |

## 生命周期规则

| 规则 | Doorfast `r6` 行为 |
|---|---|
| 容量 | 固定 16 项，不进行运行期扩容 |
| 有效期 | 入队或重复刷新后 1000 毫秒 |
| 精确重复 | 目标地址和请求 2 字节均相同时合并，刷新有效期并累计重复次数 |
| 不同请求 | 即使目标相同，只要请求数据不同就保持独立 |
| 队列满 | 拒绝新项目，保留原队列并继续抓包服务 |
| 时间回退或溢出 | 拒绝操作且不修改队列 |
| 过期 | 事件循环移除并记录过期数和剩余数 |
| 取出 | `r7` 由单事务状态机按 FIFO 取出；一次只处理一个对象 |

容量、有效期和重复合并是 Doorfast 的本地资源与失效策略，不是从旧 APK 推导出的协议常量。旧 APK 的静态证据只支持收到 `07/01` 后立即构造 `07/81`，以及回复载荷的来源。

## 运行时日志

有效请求会记录 `accepted`、`reply_pending`、`peer_observed`、`pending`、`coalesced` 和 `queue_full`。过期清理记录 `peer_reply_expired`。日志不包含完整逻辑地址、公共头字段或原始载荷。

`r6` 的队列生命周期由 C 测试覆盖。`r7` 的目标机脚本改为连续注入两次固定 `07/01`，要求每个对象都经实际抓包入口形成独立的模拟成功事务；重复合并仍由确定性单元测试验证。

## 本地复现

```sh
make clean
make test doorfast peer-sim peer-udp-inject
python3 -B -m unittest tests/test_gvs_peer_udp.py
sh tests/test_gvs_peer_sim_cli.sh
sh tests/test_package_manifest.sh
```

当前实现不证明真实门口机接受性。发送成功、失败、重试和超时目前都是离线事务语义；`mode=simulated` 不能视为报文已经到达设备。
